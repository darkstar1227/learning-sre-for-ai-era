# Day5 `speak-human-tw` 審查建議

1. **觸發位置**：第 23 行
   **原句**：它們可以由不同團隊負責，也可能由同一群人同時實踐。真正該比較的不是職稱，而是問題、方法與產出。
   **為什麼要改**：「真正該……不是……而是……」是常見的否定式排比，也把判斷寫得太像金句。
   **建議怎麼改**：它們可以由不同團隊負責，也可能由同一群人同時實踐。比較三者時，應看它們處理的問題、採用的方法與留下的產出。

2. **觸發位置**：第 57 行
   **原句**：先別急著畫組織圖。名稱會隨公司改變，問題不會。
   **為什麼要改**：後半句刻意壓成對仗短句，讀起來像預先設計的金句。
   **建議怎麼改**：先別急著畫組織圖。各公司的團隊名稱不同，前面三類問題仍然需要有人處理。

3. **觸發位置**：第 65 行
   **原句**：DevOps 最適合被理解成一組文化、實踐與協作方式，而不是某一套工具，也不只是把 Ops 改名成 DevOps。
   **為什麼要改**：一句內連用「而不是」「也不只是」，否定式解釋太密。
   **建議怎麼改**：DevOps 是一組文化、實踐與協作方式。安裝一套工具，或把 Ops 改名成 DevOps，都不會自動改變團隊的工作方式。

4. **觸發位置**：第 81 行
   **原句**：它最重要的產出不一定是一個平台或一份 SLO，而是更快、更安全且能持續回饋的工作方式。
   **為什麼要改**：「最重要」「不一定是……而是……」再次使用同一種結論公式，三個形容詞也稍微像宣傳文案。
   **建議怎麼改**：DevOps 要改善的是工作方式：縮短交付週期、減少變更風險，並讓 production 的結果持續回到開發流程。

5. **觸發位置**：第 150 行
   **原句**：平台不是把所有工具集中放在同一個入口就算完成。它有使用者，也要處理 adoption、usability、reliability 與 feedback；換句話說，平台本身是一個產品。
   **為什麼要改**：「換句話說」重述前句，且抽象英文名詞一次堆疊過多。
   **建議怎麼改**：把工具集中到同一個入口，還不算完成平台。平台團隊需要知道誰在使用、哪裡難用、服務是否可靠，以及回饋如何進入下一版；這些都是產品工作。

6. **觸發位置**：第 306 行
   **原句**：更重要的是，不要第一天就打造宇宙級平台。
   **為什麼要改**：「更重要的是」是解說型填充語，刪掉不會損失資訊。
   **建議怎麼改**：也不要第一天就打造宇宙級平台。

7. **觸發位置**：第 456 行
   **原句**：今天最重要的理解是：
   **為什麼要改**：這是預告式導言，下一行引用已經能直接表達結論。
   **建議怎麼改**：刪除此句，直接保留下一行的結論。

8. **觸發位置**：第 473 行
   **原句**：真正能留下 Evidence 的，是清楚的使用者期待、可操作的工程方法、可自助的能力，以及出了問題之後仍能走完的 feedback loop。
   **為什麼要改**：「真正能」加上四項抽象名詞，像刻意收束的口號。
   **建議怎麼改**：Evidence 應該連回四件事：使用者期待、工程決策、自助能力，以及事故後仍能運作的 feedback loop。

9. **觸發位置**：第 493 行
   **原句**：可靠性是共同結果，但共同負責不等於沒有人負責。
   **為什麼要改**：句子採用對仗與否定收尾，像獨立於上下文的金句。
   **建議怎麼改**：可靠性需要多人合作，但每項結果仍要指定明確的負責人。
